agent-replay

Records an AI agent's sessions: every tool call it made and the result it got. Then it replays them against a new model, a new prompt or new tool definitions, and compares what the agent did, not what it said. A destructive call the agent never made before fails the check.

A prompt edit or a model upgrade is usually checked by reading answers, and an answer can read the same while the actions behind it change. "Freed 41.2 GB on build-04" is a fine summary of archiving two months of CI logs, and an equally fine summary of deleting them. agent-replay looks at the calls, which is where the difference is, and it replays the unchanged agent too, so the agent's usual run-to-run variation isn't mistaken for a regression.

1Record what the agent did

A session is one JSON file: the system prompt, the tool definitions and the transcript in Messages API form, plus the optional MCP annotations on each tool. The calls the agent made, and the result each one got, are read out of the transcript.

  • From your own code: RecordingClient wraps an anthropic.Anthropic() client, passes each messages.create through unchanged and writes the conversation so far.
  • With agent-replay run, which drives the loop itself against a Python execute(name, args) that really runs the tools.
  • From any MCP client: record-mcp goes where the server command was, passes the stdio transport through unchanged, and logs each tools/list and tools/call with its result.
  • A proxy never sees the prompt or the model's text, so import-mcp adds the task, and the system prompt if you have it.

2Replay it, and execute nothing

The recorded opening messages go to the model under test with the system prompt and tools, or the replacements given with --system and --tools. Each call the agent makes is looked up by tool name and exact arguments, and a recorded call gets its recorded result. No tool ever runs.

  • A call made twice gets its results back in recorded order.
  • A call that was never recorded has no honest answer, and is usually the finding. --on-unrecorded decides what happens next: stop ends the run there, error returns an error result, stub returns a canned result from --stubs.
  • Annotations are agent-replay's own field and are stripped before each request, so they never reach the model.
  • A real model can't be seeded, so --repeat N takes N real samples. A scripted agent takes the run's seed and replays exactly.

3Compare the calls, not the text

Each run's calls are lined up with the recorded ones in three passes, and every call on both sides ends up accounted for.

  • Anchor. Calls with the same tool and the same arguments, in the same order on both sides, are matched first, with Python's difflib.SequenceMatcher.
  • Moves. An identical call left over on both sides was made at a different point, and counts once, as moved.
  • Pairs. Between anchors, two calls to the same tool are one call with changed arguments, listed field by field. Anything else was added or removed.

Property tests check the first two promises on random call lists: nothing goes missing, and a shuffle of the same calls shows up only as moves.

4Know which calls can't be undone

Every call is read-only, a write, destructive or unknown. Rules come first, then the tool's MCP annotations, then nothing.

  • Rules from a TOML file match a tool name and, optionally, its arguments, so one http_request tool can be a read with GET and destructive with DELETE.
  • Annotations are read the way the MCP spec defines them: readOnlyHint defaults to false and destructiveHint to true, so an annotated tool that claims neither counts as destructive.
  • No annotations and no rule: unknown. --strict treats unknown as destructive.
  • A rule with an unknown class or key is an error with exit code 2.

5Measure the agent against itself

Agents vary from run to run, so one difference proves little. With --noise N the unchanged configuration is replayed N more times as a baseline. Each change is counted once per run it appears in, and its rate with the edit is tested against its rate without it, with a one-sided Fisher exact test at p < 0.05.

  • Clearly more frequent with the edit: changed.
  • About as frequent without it: noise.
  • A destructive call the unchanged runs never made: DESTRUCTIVE, however rarely it appears.

Without --noise, every difference is reported, including the ones the agent makes anyway. The idea of measuring the baseline's own variation first comes from noisefloor.

6Fail the check, or only report

By default replay, compare and diff exit 1 on a destructive change, so a prompt edit or a model upgrade can run as a check in CI. A person still reads the report: agent-replay finds the change, it doesn't decide whether the change was wanted.

  • --fail-on changed also exits 1 on any significant change. --fail-on never only reports, and the verdict reads WARN.
  • --json prints the report as JSON, and --runs-out writes every run's calls as JSON lines.
  • A file it can't replay is exit 2 with a message, for example a session where the person speaks again after the agent's first turn.

7What a real model did

The same scenario, run against a real model. Claude Code was the MCP client, record-mcp sat between it and the simulated build host, and each system prompt was run five times. The ten logs and the sessions imported from them are in the repository, and compare reads them with no model call.

  • With the original prompt ("must be archived … never deleted"), all five runs archived the old logs.
  • With the edited prompt ("CI logs older than 30 days can go"), all five deleted them.
  • The model was open about it: four of the five edited replies begin "I deleted". The edit allowed the deletion. The point is that a change that looked like tidying changed what the agent does, and agent-replay turns that into a failing check.

Five runs per prompt show that the edit changes behaviour, not how often. The model name is the one the sessions were imported with: a proxy can't see which model answered.

78 tests, no API key

Counted with pytest -q -rs as CI runs it, with the optional anthropic and mcp SDKs installed: 78 passed in 5.8 to 6.9 s over three runs. Without the SDKs the 4 tests that need them skip, and 74 pass; CI runs both ways.

    The real SDKs, without the network

    • Diff: Hypothesis property tests (every call accounted for, a reordering shows up only as moves, each change points at the right side) and fixed cases, including the one that motivated anchoring on identical calls.
    • Replay: recorded results, repeated calls, parallel tool calls answered in one message, each unrecorded-call policy, refusals, the turn limit, and a check that annotations never reach the model.
    • Messages API: the adapter runs through the real anthropic SDK against a local HTTP server, which checks the request the SDK really sends and that a thinking block goes back unchanged.
    • MCP: record-mcp sits between the official mcp SDK's stdio client and a real server; traffic, server errors included, must pass through unchanged.
    • The example: the README's commands and headline numbers, and the ten Claude Code logs re-imported and compared.

    CI runs the suite on Python 3.11 and 3.13 with the SDKs, again on 3.12 without them, ruff and mypy --strict, the headline replay (which must exit 1), and make example, which must re-record the committed session byte for byte.

    Deliberately missing

    Judging text
    The final reply is scored only by string similarity, as context. An agent that says something wrong but calls the same tools passes.
    Conversations
    One person speaks first, then the agent works through tool calls. A session where the person speaks again is rejected.
    A sandbox
    Replays never execute tools, and a stub is not the world: under stub the agent sees the canned result whatever the call would have done. agent-replay run does execute, with the execute you give it.
    Loose matching
    Arguments match exactly. A call that differs only in a timestamp or a generated ID has no recorded result.
    A live API run
    The Messages API adapter is tested through the real SDK against a local server; no key was available while building it. The real-model results went through Claude Code and MCP.
