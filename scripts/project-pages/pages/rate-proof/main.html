rate-proof

Measures what six rate-limiting algorithms actually let through once they are deployed: several nodes behind a load balancer, each with its own clock, sharing state in a store a round trip away, sometimes restarting. Then it checks its own simulator against a real Redis.

A limiter is usually tested on one machine: send 150 requests, see that 100 get through. In production its clock is whichever node took the request, its state is a network call away, and the store can come back empty. None of that shows up in a unit test, and each one changes how many requests reach the service behind it.

1Six algorithms, written for a store

Each limiter is a function of one key's stored state, the time it is told, and the limit, which is how it runs inside Redis. Every one is configured as 100 requests per second.

  • Times are integer microseconds, and the buckets keep their tokens scaled so a refill is never fractional. The Lua scripts can then do the same arithmetic exactly.
  • Each algorithm states its own promise, and every admit is checked against it at the true time it was decided.
  • "100 per second" means different things. Fixed window allows 200 in one second around a window edge, and the three buckets allow a full burst on top of the refill. Only the sliding log holds 100 in every second.

2Give every node its own clock

Requests land on one of four nodes at random. Each node tells the store the time by its own clock, and the clocks are spread evenly across the skew. The store is a round trip away, each leg jittering by 25%, and a script runs when it arrives, one at a time.

  • The token bucket stores last = now on every call. A node whose clock is behind moves last back, and the next node that is ahead is refilled for the same 50 ms again.
  • The leaky bucket does the same arithmetic mirrored, but keeps last = max(last, now). GCRA stores one timestamp that only moves forward.
  • At 50 ms of skew the token bucket refuses nothing: the whole flood, five times the limit, gets through. On the flood the other two admit 0.2% more than one node with a true clock would.

3Attack every deployment the same way

Every run sends the same four clients, each on its own key, and the arrivals depend only on the seed. So every algorithm and every deployment sees exactly the same requests.

  • A flood at five times the limit; boundary bursts of 100 just before a window edge and 100 just after; the flood switched on for 2 s and off for 3 s; and an honest client sending evenly at 90% of its limit.
  • Deployments: node clocks 50 ms apart, the store's own clock (Redis TIME), a store wiped once, and no store at all, each node enforcing a quarter of the limit and restarting now and then.
  • Over compares a deployment with the same algorithm on one node, so it separates what the deployment did from what the algorithm does by design.

Reading the store's clock instead brings every peak back to its one-node value. Splitting the limit across nodes fails both ways: 5 to 11% too much gets through, and an honest client is turned away up to 6.6% of the time.

4Check the checker with planted bugs

A checker that never finds anything proves nothing. rateproof mutants runs where every promise must hold exactly: 4 nodes, a 1 ms round trip, clocks in agreement, nothing restarting.

  • All six correct algorithms, in store-backed and local deployments, must stay clean on every seed.
  • Six planted bugs must each break their promise. Four are one line away from a correct algorithm; two are deployment mistakes: a GET, a decision in the app and a SET, and local limiters each given the full limit.
  • CI runs it on 200 seeds of 12 s each, with all four traffic patterns.

ProvenAbove this line everything is a model, deterministic by seed. Below it, the same algorithms run as Lua in a real Redis, and the model has to reproduce what Redis did, admit for admit.

5The same arithmetic, in Lua, in Redis

Each algorithm is also a Lua script in redisx/lua, sharing a prelude that reads Redis TIME. rateproof redis sends the same calls to the script and to the Go code the simulator runs, and compares every decision and every stored value.

  • The calls step across window edges, sit idle for seconds, and 15% come from a clock up to 60 ms behind.
  • Lua numbers are doubles, so stored values are written with %.0f to stay exact integers past 14 digits.
  • Six algorithms, 20,000 calls each: 120,000 decisions, none different.

6Live traffic, replayed through the simulator

Four goroutines, one connection each, play the simulator's own arrival schedule against Redis in real time, 6 s per case. For every request it records when the node sent it and when Redis ran it, by Redis's clock.

  • The simulator is then handed those timings and recomputes every decision with its own model of the store. --check fails unless the count matches within 0.5% and the peak within 0.02.
  • The last column gives the simulator only each step's mean delay. For atomic scripts that is close; for the non-atomic GET and SET it misses most of the race, because timers wake goroutines in clumps, and clumps race.
  • So the tables above, which model a 1 ms round trip, are a lower bound for the non-atomic race.

Measured, not assumed

What skew does as it grows, how the real-Redis check holds up across runs, and what all of it costs to run. One Linux machine, an i5-12400F that other jobs were also using.

Skew, swept from 0 to 200 ms

Most admitted in any one second, as a multiple of the limit, worst of 10 seeds, against the skew between node clocks in ms. 4 nodes, 1 ms round trip.

The token bucket passes 2.8x at 10 ms and reaches 5.79x at 50 ms, where it refuses nothing. The leaky bucket and GCRA draw the same line and never pass 2.08x. rateproof sweep --svg regenerates the README's chart byte for byte.

Redis, run after run

The live half uses real timing, so its numbers move. What must not move is that the simulator matches each run.

The README's run and three here. All passed --check, and the replay matched Redis exactly except once: *run 1's non-atomic case, where it said +24.7% and 748 admits against Redis's 747. The differential half was identical every time: 0 mismatches in 120,000 calls.

What it costs

Wall time on this machine, with a load average around 9 to 14 from other work.

The table is 300 simulated runs of 20 s; the mutants are 3,600 runs of 12 s. The Redis run is mostly its nine 6 s live cases. With the machine far busier, a load of 44, the table took 14.9 s.

33 tests, two of them against Redis

Counted with RATEPROOF_REDIS=localhost:6379 go test -count=1 -json ./...: 33 tests, all passing, no subtests, in 13 to 16 s. Without RATEPROOF_REDIS, 31 pass in a few seconds and the two Redis tests skip. CI runs them on Go 1.22 and stable, and the Redis ones against a redis:7-alpine service.

    Tests that would fail if the claims were wrong

    • Algorithms: a full burst and no more, the refill rate, fixed window's 2x across a boundary, the sliding log holding its window, the token bucket refilling twice when the clock steps back, and each planted bug breaking its promise on some input.
    • Simulator: the same seed gives the same run, every deployment sees the same traffic, one node with no latency equals the ideal, correct deployments keep their promises, every planted bug is caught.
    • The README's findings: the token bucket collapses under skew while the leaky bucket holds, local split turns away an honest client, a wiped store hands out a fresh burst, boundary bursts peak at 2x for fixed window.
    • Redis: every algorithm has a Lua script, the RESP client's replies and errors, the Lua and Go decisions call for call, and live runs the simulator must reproduce.

    CI has four jobs: tests on Go 1.22 and stable with -race, the mutants on 200 seeds, the Redis check, and a check that docs/skew.svg is what the current code draws. The run on 38d4084 passed all five job runs.

    Deliberately missing

    Production traffic
    All four clients are synthetic. Real traffic has other shapes, and the numbers are for these.
    Drift
    Each node's clock offset is fixed. Clocks that drift or jump, such as an NTP step, are not modelled.
    Clusters
    One store and one key per client: no Redis Cluster, no replication lag, no failover beyond the store losing everything once.
    Real machines
    The Redis check ran clients and Redis on one host, with skew injected into the time sent.
    Your library
    These are the algorithms written plainly, not any library's code. To measure a library, port its script into redisx/lua and limiter/.

cd rate-proof
