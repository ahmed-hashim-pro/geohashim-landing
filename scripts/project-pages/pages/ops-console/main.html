ops-console

A real-time operations dashboard in Angular 22: zoneless change detection, signals, standalone components. 5,000 services stream status, metrics and alerts at 10,000 events a second, the screen holds 60 frames a second while you search and sort, and every feature works from the keyboard alone.

Live dashboards go wrong in two ways. Work done per event turns into dropped frames and a search box that lags. And accessibility breaks: rows move under the keyboard focus, a screen reader announces every update, nothing can be paused. This repository treats both as claims to measure, with frame timings from Chromium, axe audits, and Playwright tests that only press keys.

1A stream you can replay

A Node server with no dependencies serves the built app and an SSE endpoint that sends one message per event, as most real event sources do. How the client copes with that is the point of the app.

  • The events are a pure function of a seed and the fleet size, so the tests, the perf runs and the demo all see the same stream.
  • Each event is a small array, and the server stamps its send time as the last element. That is how the app measures data age.
  • If the client can't keep up, the socket fills and the server waits for it to drain. Events are delayed, never skipped.
  • A reconnect asks for from=<count>, so the sequence continues instead of restarting.

2Four ways to apply an event

Four stores implement one interface. The components, the ordering and the stream are shared, so a perf run compares exactly one thing: what a single event does on its way to the screen.

  • Batched, the default: newest values go into typed arrays, and once per animation frame they are applied and one signal is bumped.
  • Eager: the same store, applying each event and bumping its signals at once.
  • Naive: what a straightforward signal store does, a new 5,000-entry list per event, then set the signals.
  • Zone: the eager store in a zone.js build, where change detection runs after every event handler.

A unit test feeds the same 30,000 generated events to batched, eager and naive and requires the exact same end state. It caught one real bug: Float32 buffers had turned 43.7 into 43.70000076.

3Find where each one breaks

perf/run.mjs drives the production build in Chromium at 1400 by 900. Each condition gets a fresh page, 5 seconds of warm-up and 20 seconds of measurement, while a scripted user types into the search box every 500 ms. The page records its own timings.

  • Dropped frames: the frames missed between requestAnimationFrame callbacks.
  • Input delay: from each keydown to just after the next frame is drawn.
  • Data age: from the server sending an event to the end of the frame that first shows it.
  • "4x slower CPU" is Chrome's CPU throttling, the setting Lighthouse uses for a mid-range phone.

The two collapses are rendering per event and copying per event. Batching per frame isn't what saves the dashboard; eager is within noise of it. What batching buys is a cost per frame that stops growing with the event rate.

4Only the rows in view exist

The fleet is a real <table>, virtualised by hand. Only the rows in view plus six either side are in the DOM, and hidden spacer rows hold the scroll height.

  • aria-rowcount and aria-rowindex tell assistive technology where each row sits in the whole list.
  • Each row's name is a button, and only one is in the tab order. The arrow keys, Page Up, Page Down, Home and End move a roving tabindex, scrolling the row into view first.
  • The visible values re-render from one signal read, once per frame in the batched store, whatever the event rate.
  • Charts are a few lines of canvas, each with a text alternative and its numbers also shown as text.

RenderedAbove this line it is the machine's problem: how fast events reach the screen. Below it, a person is using the screen, and the rules change: nothing moves under their focus, nothing talks over them, and everything can be stopped.

5Rows hold still under the keyboard

The table re-sorts once a second. While focus is anywhere in it, the order holds, so a row never moves out from under the keyboard. The values keep updating, and a note under the table says so.

  • A new filter still applies at once, even while the order is held.
  • The alert list works the same way: while focus is in it, new alerts wait behind a "Show N new alerts" button.
  • When a pressed button disappears, such as Acknowledge becoming Acknowledged, focus moves to its replacement. Closing details returns focus to whatever opened them.

Scrolling the focused row out of view with a mouse removes it from the DOM, and focus goes back to the page. Keyboard navigation always keeps it in view. The README lists this.

6One sentence every ten seconds

Two polite live regions. One speaks the result of something the user did, at once. The other sums up new alerts at most once every ten seconds, so a burst of fifty alerts is one sentence, not fifty.

  • The level is a choice: critical alerts only, the default, all alerts, or off.
  • Status is never shown by colour alone. A shape and the word go with it, in the table and the tiles.
  • A Playwright test watches the region for 21 seconds while dozens of alerts arrive, and allows at most three announcements.

Nobody has used it with NVDA, JAWS or VoiceOver yet. The roles, names, live regions and focus order are tested automatically; the README says a screen reader is where the live regions and the virtual table would most likely find something.

7Checked from the keyboard alone

Every feature has a Playwright test that never clicks and never calls focus(): skip link, search, status filters, region and sort, row navigation, details, silence, acknowledge, pause, theme and the shortcuts dialog.

  • axe-core finds no WCAG 2.1 A or AA violations in four audits, in both themes: streaming, details open with an alert acknowledged and updates paused, the shortcuts dialog, and a search with no results.
  • p pauses updates (WCAG 2.2.2), and the single-key shortcuts can be turned off (2.1.4).
  • A node test checks every colour-token pair in both themes. On the first CI run it caught a selected row's name at 4.34:1 in the dark theme, which hadn't shown locally.
  • With reduced motion, a test requires that nothing on the page has a transition or an animation.

Four CI jobs

CI's perf job checks only the batched store, against thresholds well below what the README's machine shows: frame p95 50 ms, dropped 25%, input p95 150 ms.

60 tests: unit, server and browser

Counted the way CI runs them: npm test runs ng test (Vitest, 24) and node --test on the server and contrast tests (8), and npx playwright test runs 28 against the production build. All passed here.

    What they pin

    • The stores: any number of events folded into one update per frame, status counts, alerts raised, acknowledged, silenced and resolved, pause and catch-up, at most 500 alerts, and three stores ending in the same state on 30,000 events.
    • The view and table: sort and filter, re-ordering on the tick and not on every change, the held order, a rendered window of rows with each one's position, and exactly one row in the tab order.
    • The server: a stream that is a pure function of its seed, the rate asked for and a resume where told, and bad parameters and paths outside the app refused.
    • Contrast: every colour pair in both themes, and the old selected-row colour that would have failed.
    • The browser: keyboard-only tests for every feature, axe in both themes, batched announcements, reduced motion, and each store streaming without console errors.

    CI also runs the perf check at 10,000 events a second and the ten-minute soak on every push.

    Deliberately missing

    A screen reader trial
    Roles, names, live regions and focus order are tested automatically, but nobody has used it with NVDA, JAWS or VoiceOver.
    Other browsers and devices
    One machine, headless Chromium, loopback. Firefox, Safari, real networks and real phones weren't measured.
    Real data
    The rates, alert mix and incidents are a model, and acknowledgements and silences live only in the page.
    The worst store
    The naive store is one common pattern. One that also re-sorted per event would do worse, and a per-entity signal store would do better.
    Being a product
    No authentication, persistence or alert routing. It is a front end and a test bench.
