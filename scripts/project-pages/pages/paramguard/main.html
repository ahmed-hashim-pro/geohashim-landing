paramguard

A CI check for PX4 and ArduPilot parameter files. It reads a parameter change the way the vehicle will, and blocks the pull request when the change turns off a failsafe, misspells a name, leaves the firmware's documented range, or steps a control gain too far.

A parameter file decides what a drone does when the radio link drops, the battery runs low or the fence is crossed. Teams review these files as text diffs, but the vehicle runs values. Delete a line and the vehicle falls back to the firmware default, which for PX4's link-loss failsafe is "do nothing". Misspell a name and the line sets nothing at all. Neither looks wrong in review; paramguard says why each one is.

1Read the file the way the vehicle's loader does

A parameter file can be a QGroundControl export, a PX4 startup script, or plain NAME VALUE and NAME,VALUE lines from ArduPilot and Mission Planner. paramguard reads all of them, mixed in one file if need be, and compares values, not text.

  • Floats are compared as the float32 the autopilot stores, so 0.15 and QGroundControl's 0.15000000596046448 are the same value. Line order never matters.
  • QGroundControl's type column is checked: an integer parameter written with a fraction is refused.
  • Any line it can't read stops the run with the file and line number, and exit code 2. A file that is half read is worse than one that is refused.
  • A name set twice is an error, because which value wins depends on the loader.

2Compare what the vehicle will run, not the lines

Each parameter's effective value is the file's value, or the firmware default when the file doesn't set it. The defaults come from the firmware's own metadata. A change is any parameter whose effective value moved.

  • Deleting a line is a change whenever the deleted value wasn't the default. That is the change a reviewer reads as harmless cleanup.
  • Writing a default out explicitly changes nothing, so tidying a file in either direction is quiet.
  • A file that is new on the branch is compared with the firmware defaults.

In PX4 v1.15.4 the default for NAV_DLL_ACT, the ground-station link-loss failsafe, is 0: disabled. PX4's simulated planes set it to 2 at start-up, which is why a value of 2 looks like a default to anyone who has used them.

3Check every changed line against the firmware's metadata

Every PX4 build generates a parameters.json with each parameter's type, range, enum values, bitmask bits and default. paramguard ships the v1.15.4 SITL build's copy, and --meta points at any other build's, or at ArduPilot's apm.pdef.xml.

  • unknown-param: the vehicle has no parameter by that name, so the line sets nothing. It suggests the name you meant.
  • out-of-range, not-in-values, not-integer and unknown-bits: PX4 stores such values without complaint. Checked for this page on a fresh PX4 v1.15.4 SITL: it stored and read back MPC_Z_VEL_MAX_DN = 5 against a maximum of 4, MC_ROLLRATE_P = -1 and NAV_DLL_ACT = 4, and answered MPC_XY_CRUSIE with nothing but an error on its own console.
  • A problem already in the base version is reported as a note, not a block, so adopting paramguard doesn't fail on a vehicle's history.

4Judge each change against rules that say why

A rule names parameters, a condition and a reason written for the reviewer. The built-in PX4 set covers failsafes, the geofence, circuit breakers, airframe and motor mapping, and tuning steps. Your own TOML rules add to it.

  • Conditions: forbid, allow_only, min, max, no_decrease, no_increase, max_step, no_sign_flip, any_change, no_new_bits and below, on names or globs.
  • Rules are checked against the metadata before anything runs. A misspelt parameter, a glob that matches nothing, an unknown key or a missing reason is an error: a rule that silently never fires is the failure this tool exists to prevent.
  • A rule is block or warn. Only a block fails the check.

AllowedAbove this line paramguard reads, resolves and checks, and any block fails the pull request. Below it, a block passes only with a committed allowance that names who accepted it and why.

5A named person accepts one exact value

Some blocked changes are right: a tethered vehicle doesn't need a link-loss failsafe, and a retune after a prop change does move gains a long way. An allowance in paramguard.allow.toml accepts one finding, and it must say who and why.

  • It covers one rule, one parameter and one value, or "removed". If a later change moves the gain again, the block comes back.
  • An allowance that no longer matches anything is reported, so a stale one can't be mistaken for one that still covers something.
  • An allowed finding is still printed, with the name and reason, so the decision stays in git next to the parameters.

6Run it on every pull request

paramguard check --base origin/main vehicles/*.params compares each file with its version on the base branch, read with git show. As a GitHub Action it does the same against the pull request's base, and --format github puts each finding on the diff, on its line.

  • Exit 0 when nothing blocks, 1 when something does, 2 when an input can't be read.
  • Action inputs: files, base, meta for your board's build, rules and allow.
  • The repository runs its own action in CI, and flies the link-loss comparison in PX4 SITL on every push.

67 tests, one of them needs ArduPilot's file

Counted with pytest -q: 66 pass and one skips. The skipped test checks the built-in ArduCopter rules against ArduCopter 4.6.3's own metadata, which is GPL-licensed and not bundled; with it downloaded, as make ap-meta and CI do, all 67 pass.

    Aimed at the ways a reviewer gets fooled

    • Parser, metadata and rules: every line format, every format error with its line number, every rule-file mistake and rule condition. The built-in rules are checked against the bundled metadata.
    • Both example pull requests end to end, plus allowances, cross-parameter below rules, notes for problems already in the base, and ArduPilot without defaults.
    • Properties, with Hypothesis: a file against itself changes nothing; line order never matters; writing out a default never changes the result; the link-loss rule blocks exactly when the value becomes 0; the range check agrees with the metadata; an allowance covers its own value and no other.
    • The CLI: exit codes, JSON, GitHub annotations, --base against a real Git repository, allowance files, and quiet output when piped into head.

    CI runs ruff, mypy and the tests on Python 3.11, 3.12 and 3.13, checks the ArduCopter rules against 4.6.3's metadata, runs the action on the repository's own example, and flies the SITL comparison.

    Deliberately missing

    A proof of safety
    It catches the kinds of change it has rules for. A file that passes can still fly badly; tuning needs flight testing, and the gain-step rule only stops big jumps between tests.
    Your vehicle's limits
    The built-in thresholds, 20 m return altitude, 3 m/s descent, a 50% gain step, are general multicopter sense. Put your own numbers in your own rule file.
    Your board's defaults
    The bundled metadata is PX4's SITL build. A flight-controller build adds driver parameters and airframe scripts change defaults, so point --meta at your build's parameters.json.
    A whole new file
    check judges changes, and a new file is compared with the firmware defaults, so a new vehicle file that never sets NAV_DLL_ACT passes it. paramguard lint judges a file on its own and blocks it.
    The vehicle itself
    It checks files in a repository. A parameter changed from a ground station and never committed is invisible to it, and no real aircraft flew: the flight above is SITL.
