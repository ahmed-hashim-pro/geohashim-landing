permit

A CLI and GitHub Action that reads a dependency upgrade the way a security reviewer would. It asks one question: what can the new code do that the old code couldn't? Anything new blocks the pull request until a person allows it.

Most supply-chain attacks on npm arrive as an ordinary-looking version bump, and a lockfile diff only shows version numbers. permit fetches the versions the lockfile changed, parses their code, and subtracts what the package could already do. Opening a network connection, running an install script or reading the environment is a capability the upgrade has to be granted.

1Read both lockfiles, strictly

permit compares two package-lock.json files, the base branch's and the pull request's. It reads only the packages section, which lists what actually lands in node_modules.

  • Every package version installed after but not before is looked at. A name that existed before at another version is changed.
  • A name that is new to the tree is new, and everything it can do counts as new, because a fresh transitive dependency is how most attacks arrive.
  • Only lockfile versions 2 and 3. A v1 lockfile, a malformed entry or a version that isn't semver is an error that names the entry, with exit code 2.
  • Workspace links and workspace packages are local code, not downloads, and are skipped.

2Fetch the bytes npm would install

Each changed version is downloaded, along with every version of that package installed before, from the URL the lockfile resolved to, or the registry's usual one. The tarball must match the lockfile's integrity hash, so the code analysed is the code npm would install.

  • A hash mismatch is an error, never a warning.
  • Unpacking writes regular files only. Symlinks and hard links are skipped, and an entry whose path would leave the package directory makes the whole tarball refused.
  • Downloads run eight at a time, with three attempts on a network error or a 5xx and none on a 4xx. Good tarballs are cached by name, version and hash in $XDG_CACHE_HOME/permit, or ~/.cache/permit when that is unset. A refused tarball leaves nothing in the cache.
  • A package that can't be fetched or read doesn't pass. It is reported as unanalyzable and blocks like any other gain.

3Parse the code, don't grep it

Every .js, .cjs and .mjs file is parsed with acorn and walked. A comment or a string that mentions child_process isn't a use of it, and a use that never spells the word is still found.

  • require and process are followed through aliases such as var r = require, because that is how obfuscated payloads hide them.
  • What can't be resolved is reported, not dropped: a require() of a computed name is dynamic-require, and any computed property of process counts as env.
  • Package-level checks too: install scripts in package.json, a binding.gyp, and ELF, Mach-O, PE or .node binaries by their magic bytes.
  • A file that doesn't parse, or one over 4 MB, is unanalyzable. Each capability keeps the file and line where it was first seen.

In the repository's event-stream example the network code sits inside an encrypted string, so network can't be seen. An aliased require of a decoded name and a computed read of process can, and that is enough to block it.

4Subtract what was already there

The gains are the new version's capabilities minus everything any previously installed version of that package had. A package that always used the network, or always ran an install script, is not news. A patch release that starts to is.

  • The subtraction is per capability, not per file or line, so moving code around inside a package doesn't raise anything.
  • A changed package also lists its new dependencies, which then appear as new packages in their own right.
  • Any gain the policy doesn't allow blocks: permit exits 1 and prints the line to add to permit.json. It never edits the policy itself.

5A person allows it, by name

permit.json in the repository root lists, per package, the capabilities a person has reviewed and expects. "*" applies to every package. Only what is listed passes.

  • An allowed gain is still printed, marked allowed, so the review trail stays in every report.
  • Allowing network doesn't allow env. Each capability is granted on its own.
  • A misspelt capability or an unknown key is an error with exit code 2, not a silent allow or a silent deny.

6Run it on every pull request

As a GitHub Action, permit compares the base branch's lockfile with the pull request's, writes the report to the job summary, and fails the check when anything new isn't allowed. Inputs: base, lockfile and policy.

  • permit diff --base <ref> reads the old lockfile with git show, so the same check runs locally before a push.
  • The action builds permit from its own source with npm ci, then runs the same diff --base.
  • The repository runs its own action on its own lockfile in CI, as a user would.

36 tests, no network

Counted with npm test, which runs tsc -p . and then node --test dist/test/*.test.js: 36 tests, all passing. The download and cache test starts a local HTTP server inside the test, and the retry test swaps in a fetch that fails on cue.

    Weighted toward what an attacker would try

    • Analyser: 26 snippets, one per detection route, and code that must not trigger: comments, strings, look-alikes such as obj.writeFileSync.
    • Property test: 500 files assembled at random from snippets with known capabilities, mixed with harmless code and decoys. The detected set must equal the union exactly.
    • Sources: a tar writer in the tests makes pax long names, symlinks, hard links and path-traversal entries, and a refused tarball must leave nothing in the cache; a real npm pack tarball; SRI hashes; download, cache, 404, and retry on a network error and on 503.
    • Lockfiles and policy: nested, scoped and aliased packages, workspace links, and every class of malformed input.
    • Diff and CLI: the three examples end to end, a capability any earlier version had, an unfetchable package, exit codes 0, 1 and 2, --json, and --base against a temporary Git repository.

    CI runs prettier, tsc --strict and the tests on Node 20 and 22, checks that examples/ matches its generator, and runs the action on the repository's own lockfile.

    Deliberately missing

    A guarantee
    It is static analysis and can be evaded, for example by building require from globalThis["req" + "uire"]. It raises the cost of a quiet upgrade; it doesn't replace --ignore-scripts or reviewing what it flags.
    Call paths
    Capabilities are per package. A package that uses https only in a CLI you never call still has network; allow it once.
    Other lockfiles
    npm only, for now. No yarn, pnpm or bun. Packages from git or local paths can't be fetched as tarballs and are reported as unanalyzable.
    A vulnerability database
    It says what a version can newly do, not whether it has a known CVE. That is npm audit's job.

    git clone https://github.com/ahmed-hashim-pro/permit
cd permit
npm ci && npm run build
npm test            # 36 tests, offline

# The examples, offline:
cd examples/ua-sniff
node ../../dist/src/cli.js diff before.json after.json \
  --fixtures ../../fixtures/packages

# Your project, against the real registry:
node dist/src/cli.js diff --base origin/main

    Node 20 or newer. The examples need no network. Against the registry, tarballs are cached in ~/.cache/permit (or under $XDG_CACHE_HOME), so the second run of the same diff is fast.
