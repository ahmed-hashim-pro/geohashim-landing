atlas-graph-db

A graph database written from scratch in TypeScript: an embedded engine with a write-ahead log, crash recovery and atomic transactions, a Cypher-like query language called AQL, a multi-user server and a web explorer.

It was built to learn how a database really works, and that meant making one come back correctly after a crash. Durability came first: the log, then snapshots, then recovery tested by killing the process mid-write. Indexes, traversals, graph algorithms and AQL were built on top of something that already survived that.

1Parse the query, then pick where to start

AQL goes through a hand-written lexer and a recursive-descent parser, then a planner. The planner starts each pattern at its cheapest node: an index seek when an equality hits an index, otherwise a scan of the label with the fewest nodes.

  • Reads stop here and run against committed state. A write statement goes on to stage 2 as one transaction, so any error rolls the whole statement back.
  • Errors carry a code, a line, a column and a caret under the problem.
  • Runtime guards raise TIMEOUT or ROW_LIMIT instead of returning a quietly cut result.

2Stage every change in memory

A transaction is a synchronous callback that stages ops in a list. Nothing touches the graph or the disk while it runs, so throwing the list away is the whole rollback.

  • References are checked against the transaction's own view: an edge to a missing node, or deleting a node that still has edges, fails at once.
  • Unique constraints are checked against the batch's final state, before a byte is written.
  • An async callback is refused. Ops staged after the log write would leave memory and disk disagreeing.
  • Rejected transactions still use up node ids in that process. After a restart, numbering resumes from the highest id in the log.

3Write one record, fsync, then say yes

The staged ops get the next transaction id and become one record: an 8-byte header holding the payload's length and a CRC-32, then the MessagePack payload. There is no begin or commit marker. A transaction is atomic because it is one checked record.

The caller hears yes only after the record is written and fsynced. If the write or the fsync fails, the commit is rejected, and the log writer refuses everything after it until the database is reopened, so nothing can be acknowledged behind a damaged record.

A failed fsync is the hard case. The bytes may already be in the file, so a commit rejected at that step can be there after a restart. Its outcome is unknown, not rolled back. The server always runs with an fsync on every commit.

ClearedThe record is in the log and fsynced. Only now does the transaction change the graph that readers and subscribers see.

4Apply it, then tell subscribers

Only after the append resolves does the batch touch the in-memory graph, its adjacency lists and its indexes. The batch object that was logged is the one applied, so memory and disk can't drift apart. Then the change feed emits it, and the server forwards it over WebSocket.

  • Short reads take no locks and always see whole committed transactions.
  • Long reads and graph algorithms take a read lease that holds the write queue, so they see one point in time.
  • Commits go through one queue, one at a time, each with its own fsync: 200 commits fired at once still made 200 fsyncs.

5Fold the log into a snapshot

Replaying a long log is slow, so once it passes 64 MiB, or on request, the database writes a snapshot of the whole graph and starts a new log segment.

  • Inside the write queue: close the log, open the next segment, encode the graph to memory. Writes pause for this part.
  • Outside it: write a temporary file, fsync it, rename it, fsync the directory, then delete what the snapshot covers.
  • A crash at any step leaves something recovery can use: a stray temporary file is deleted on open, and a segment the snapshot already covers is ignored, then removed.

6Recover whole transactions, nothing else

On open, the database loads the newest snapshot, then replays newer log records in order. Each record's length and CRC must check out, and transaction ids must follow on without a gap.

  • A short or corrupt record at the end of the last segment is a torn write. The file is cut back to the last whole record, with a warning.
  • A gap in transaction ids, or damage in an earlier segment, is refused outright with WAL_CORRUPT.
  • The repo's crash test kills a writer five times at random moments and checks for whole transactions only, and at least everything that was acknowledged.

The rule has a cost. A flipped bit in the middle of the last segment looks just like a torn tail, so recovery also drops the intact records after it, with only a warning.

Measured at the capacity point

The design spec set its targets before any code: 1 million nodes and 5 million edges, recovery under 30 seconds, under 8 GB of heap. These figures were re-run for this page on one laptop (macOS, 12 cores, 18 GB, Node 26) with the repo's own synthetic generator and seed. Each reopen ran in a fresh process.

The log writer can share one fsync between appends, but each transaction waits for its own before the next starts. Bulk loads go fast by putting many ops in one transaction instead; the benchmark uses 10,000. On this laptop that meant about 340 to 390 small commits a second.

686 tests, durability first

468 Vitest tests across the six packages and 218 Angular tests for the explorer, all passing. The engine's suite does what a crash would: it kills processes, tears records and replays logs.

    Weighted toward what fails silently

    • Crash: a child writer is killed with SIGKILL five times at random moments after its first durable commit; recovery must hold whole transactions only, at least everything acknowledged, and the index. On failure the test keeps the data directory as evidence.
    • Property-based: 25 runs of up to 60 random actions with a snapshot every 2 KiB, then a reopen that must keep every invariant, the same counts and the same index definitions.
    • The log: torn final records, bad CRCs, short writes, and the writer stopping after a failed or partial write so nothing is acknowledged behind it.
    • Transactions: a rollback persists nothing, ids are never reused across a reopen, async callbacks are refused before any write, and a gap in transaction ids refuses to open.
    • Constraints and queries: unique constraints with same-batch index changes, the parser and planner, MERGE, and write statements that roll back whole.
    • Server: auth, the permission matrix, problem-details errors, the audit log and WebSocket subscriptions.

    CI runs the build, type checks, lint, a format check and both suites on Node 22. Five Playwright end-to-end tests in apps/web/e2e run separately with pnpm e2e:web, not in CI.

    Deliberately missing

    Clustering and replication
    One node. The design spec rules out horizontal scaling for v1.
    Graphs bigger than memory
    The graph lives in RAM and durability lives on disk. Tens of millions of elements would need compact typed-array layouts, deferred on purpose.
    Concurrent writers
    One write queue, so there are no write conflicts to resolve and no MVCC.
    Snapshots with no pause
    A checkpoint pauses writes while it encodes the graph. JavaScript has no cheap copy-on-write fork, so that is out of scope.
    A strict open mode
    A damaged tail is cut back with a warning today. An error code is reserved for refusing to open instead.

    Run it

    git clone https://github.com/ahmed-hashim-pro/atlas-graph-db.git
cd atlas-graph-db

# Explorer and API on http://localhost:4848
export ATLAS_SECRET=$(openssl rand -base64 32)
export ATLAS_ADMIN_USER=admin
export ATLAS_ADMIN_PASSWORD=change-me-please
docker compose up --build

# Or build and test it locally
pnpm install
pnpm build && pnpm lint && pnpm test

    One container serves the API and the explorer from the same origin, with the data directory on a mounted volume. The packages are not published to npm; the engine can be used directly from the workspace.
