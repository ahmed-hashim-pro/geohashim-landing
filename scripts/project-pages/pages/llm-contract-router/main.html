llm-contract-router

A TypeScript library that routes a request across LLM providers, checks each answer against your schema, and tells the model which rule it broke before retrying or moving to the next model.

Falling back to a cheaper model is easy. Falling back safely is not: the weaker model returns prose where JSON was asked for, or drops a required field, and the failure lands in your application. So the hold line here protects your code from the model, not the other way round. An answer reaches the caller only after it has passed the contract.

1Shape the request for the model's tier

Every model in the chain carries a tier: frontier, balanced or compact. The tier decides how much scaffolding its request gets, so the same complete() call produces a different request for each model.

  • Every tier gets the schema. Balanced and compact also get four output rules, and only compact gets a worked example. Temperature drops from 0.2 to 0.1 to 0.
  • The worked example is generated from the JSON Schema itself, and a test checks that it passes the contract. For a shape the generator doesn't understand it gives no example rather than a wrong one.
  • A caller can override one tier, say compact's temperature, without redefining the rest.

The asymmetry is deliberate. A compact model given a terse prompt returns prose; a frontier model given all the hand-holding does worse, because the scaffolding crowds out the task.

2Call the model, fall over on provider errors

Each call runs under its own deadline, 30 seconds by default. When a call fails, the adapter has already translated the vendor's error into one small vocabulary, so the routing logic never sees a vendor error.

  • A provider failure moves straight to the next model, with no repair. A repair can fix a bad answer, not a 429; a test checks the primary is called once even when two repairs are allowed.
  • A model whose provider was never registered is skipped, not fatal, so one bad entry can't take out the rest of the chain.
  • Before every call, the spend so far is checked against an optional budget, maxCostUsd.
  • Keys come only from the apiKey option or the vendor's environment variable. A missing key fails when the provider is created, before any request.

3Pull the JSON out of the reply

Telling a model to return only JSON doesn't make it so, and the weaker the model the less it holds. So the parser tries the readings in order, cheapest first, and keeps the first that parses.

  • The whole reply, then a fenced code block, then the first balanced {…}, then the first balanced […].
  • The balanced-span scanner skips braces and escaped quotes inside strings. A regex can't: in {"note":"}"} the first closing brace is inside a string.
  • When nothing parses, that becomes a problem the model is shown on the repair, like any broken rule.

4Check the answer against the contract

This is the hold line, and it protects your code: nothing a model says gets past it unless it satisfies the contract. A contract is two things, a schema the model is shown and a validate function that decides.

  • Any validator with a zod-style safeParse fits, or a hand-written function, because the interface is structural. The library depends on no validator; its tests use real zod 4 and a hand-written contract.
  • Validator errors become path: message lines, because “invalid input” gives a model nothing to fix.
  • Three exits: pass and hand the data over; fail with a repair left and send the problems back; fail again and try the next model. Every rejection is recorded with its problems, tokens and cost.

5Repair once, naming the broken rule

A rejected answer never crosses. The model is told what it produced and exactly which constraints it broke, then asked once more. Asking again without that just re-rolls the same mistake.

  • The repair prompt carries the original ask, the model's own reply, cut at 2,000 characters, and one line per broken rule.
  • One repair per model by default. If the repair fails too, the router stops spending on a model that can't comply and moves on.
  • The next model starts clean from the original prompt and never sees the failed repair.

One test says it in its name: the router “tells the model what was wrong, not just that it was wrong”.

6Hand back typed data or a typed failure

Your code gets { ok: true, data, meta } with the data typed and validated, or { ok: false, error, meta } where the error is chain_exhausted, budget_exceeded or configuration. meta matters most when it failed, so it travels in the result rather than on an exception.

  • meta.attempts lists every call: model, tier, repair number, outcome, failure kind, problems, tokens, cost and latency.
  • degraded means a model other than the primary served it; repairs counts repair calls. Two fields, two signals.
  • costUsd sums every attempt, repairs and abandoned models included, so a fallback can cost more than the primary alone.

      Weighted toward what fails quietly
      
            
        
              
      • Routing: falls over on four failure kinds without a repair, reports every model when the chain runs out, skips an unregistered provider, and turns a provider that never answers into a timeout.
        • 
              
      • The contract: repairs instead of giving up, tells the model what was wrong, moves on when the repair fails, honours repairsPerModel: 0, and keeps degraded and repairs separate.
        • 
              
      • Calibration: each tier gets a different request, the worked example passes its own schema, a self-referential schema still terminates, and a runaway answer is cut before it's echoed back.
        • 
              
      • Parsing: fences, prose, nesting, braces and escaped quotes inside strings, and four replies it must refuse.
        • 
              
      • Adapters: the Anthropic and OpenAI wire shapes against fake clients, and HTTP status codes mapped to the router's vocabulary.
        • 
              
      • zod: the README's zod path, end to end with real zod 4.
        •

      Deliberately missing
      
            
      
              
      Streaming
      The contract is checked against a complete response, so there is nothing to validate mid-stream.
      
              
      Backoff, caching and batching
      No retries within a model beyond the one repair. A 429 falls over at once; backoff belongs on the vendor client you pass in.
      
              
      Quality measurement
      The router trusts the tier you assign and won't notice a model getting worse. Tier is a judgement, not a benchmark. Measuring that is a different tool, noisefloor.
      
              
      Shipped prices
      Model identities and tiers ship; prices don't, because a stale price that looks authoritative is worse than none. You pass current prices with withPricing.
