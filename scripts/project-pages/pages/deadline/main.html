deadline

A small Java 21 library that passes a request's time budget from service to service over HTTP. Each hop knows how long the user is still waiting, stops work nobody is waiting for, skips retries that couldn't finish, and reports where the time went.

Timeouts are usually set one hop at a time, and each looks sensible on its own. The user's app gives up after 2 s. The gateway gives orders 3.5 s and three attempts; orders gives inventory 1 s and three attempts. Together, a request the user abandoned at 2 s keeps three services busy for almost ten seconds. gRPC solves this with deadlines. Plain HTTP services usually have nothing.

1Send what's left, not a time of day

A caller sends Deadline-Budget-Ms: 1830: whole milliseconds it is still prepared to wait. The callee turns that into an instant on its own monotonic clock the moment the request arrives, so hosts with skewed clocks still agree. This is what gRPC does with grpc-timeout.

  • The cost is that network transit isn't counted. Each caller keeps a margin back for it.
  • Zero or negative means the caller had already run out. That request gets a 504 without being worked on.
  • Anything that isn't a whole number is a 400. Budgets over an hour are clamped to an hour.
  • No header means no deadline: configured timeouts, every retry, as if the library weren't there.

Building it turned up the negative case. The parser once returned -1 for both "absent" and "-20 ms", so an expired request ran with no deadline at all. A test now holds it.

2Give each attempt the smaller of its timeout and what's left

Before every attempt, Plan.next looks at the call's policy and the request's deadline. The caller waits min(timeout, remaining), and tells the callee that, less a margin, so the callee's answer gets back inside the wait.

  • An attempt with less than minUseful + margin left is never sent. It couldn't finish, so it would only add load.
  • Plan is a pure function of the policy and a deadline. Its tests run on a virtual clock that moves only when told to.
  • 200,000 random policies are checked against four invariants: the callee's budget is never spent on arrival, never more than what's left less the margin, the caller never waits past its own deadline, and the answer always fits inside the wait.

3The callee stops when the budget does

DeadlineHandler wraps a service's handler. It rejects a request that arrives with nothing left, waits for a worker slot only as long as the budget allows, and turns DeadlineExceededException from ctx.check into a 504.

  • A queued request gives up its place when its budget runs out, instead of being served after nobody is waiting.
  • Stopping is cooperative: at ctx.check(), at a downstream call, or in the queue. Nothing interrupts threads, so a long loop that never checks runs to the end.
  • Work finished after the caller hung up is still reported. An early version skipped its listener when writing the reply threw, which hid exactly the waste the demo measures.

4Send the trace back with the reply

Each hop returns its spans in a Deadline-Trace response header, with times relative to when it received the request. The caller shifts them by when it sent the request and nests them under the attempt, so the edge gets the whole tree with no clock synchronisation.

  • Every hop answers before its deadline, so the trace arrives on failures too. A 504 says which hop ran out and what it was doing.
  • Past 64 spans the rest are counted, not kept, so the header stays small.
  • A malformed header gives an empty trace, never an exception.

5One slow request, three JVMs

deadline demo starts gateway, orders and inventory as separate JVMs on loopback, with the same timeouts and retries in both runs. Inventory is having a slow day: every call takes 1.5 s. The only difference between the runs is whether the budget travels with the request.

  • Without it, the user gives up at 2 s, and nine of the twelve calls between services happen after that, for nobody.
  • With it, every hop stops when the budget runs out, and the retries that couldn't finish are never sent. The user gets a 504 before giving up, carrying inventory's own report.
  • The two runs switch only CallPolicy.withPropagate and DeadlineHandler.enforce, so the comparison is like for like.

Nagle's algorithm nearly ate the margin. The JDK server writes headers and body separately, and a small 504 sat about 40 ms behind a delayed ACK, so it reached the user just after they gave up. The services set sun.net.httpserver.nodelay.

6Under load, the waste crowds out live requests

deadline load sends 30 requests a second for 20 seconds. Inventory has 8 workers and takes 100 ms a call, except for 5% of requests, which take 1.5 s. The timeouts are the demo's, and the same requests are slow in both runs.

  • Without deadlines each slow request becomes nine 1.5 s inventory calls. Inventory's workers fill with retries for users who have left, and the fast requests queue behind them, time out, and retry in turn.
  • With deadlines a slow request costs about two seconds of inventory time and then stops, so the fast ones keep flowing.
  • --check fails the run unless deadlines answer at least 85%, at least 30 points more than without, with under 1% of work after users left, and unless the run without them wasted most of its work. CI runs it on every push.

49 tests, decisions to whole chain

Counted by Surefire under ./mvnw -B verify, as CI runs it: 39 test methods, plus 10 cases of one parameterised test of malformed budgets. All passing on OpenJDK 21.

    Weighted toward the claim

    • The decisions, on a virtual clock: the boundaries, the demo's orders hop decision by decision, and 200,000 random policies against the invariants.
    • The handler and client over real HTTP: malformed and expired budgets, work cut short, retries on 5xx but not 4xx, forwarded headers, attempts not started, and traces merged across two hops.
    • The whole chain, both ways: without deadlines inventory must be called nine times and work long after the user left; with them everything stops before the user's wait is up, with no work after it, and inventory's own report reaches the user.
    • Regressions: the negative budget and the listener skipped when the caller hung up, two of the three bugs the README records. The third, Nagle, would fail the chain test's timing.

    CI also runs demo and load --check with three separate JVMs on every push.

    Deliberately missing

    Interrupting work
    Stopping is cooperative. A CPU loop or a blocking JDBC call that never checks runs to the end.
    Frameworks
    HTTP/1.1 through the JDK only. No servlet filter, Spring or Netty integration, and no gRPC, which has deadlines already.
    Backoff and retry budgets
    Retries are immediate. Backoff, jitter and hedging reduce retry storms from another direction and would combine with this.
    Trust
    The budget header is clamped to an hour but not an authorisation boundary. A caller can always ask for more time than its own caller gave it.
    Maven Central
    Not published. Build it from source.
